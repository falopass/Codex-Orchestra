Blueprint de implementación · 12 agosto 2026

Construir un control plane profesional para Codex, Grok y Kimi.

Este documento define un producto local, privado y liviano para usar GPT‑5.6 Sol como Tech Lead/orquestador, Grok 4.6 como engineer/ejecutor y Kimi K3 como especialista frontend, manteniendo Codex Desktop como superficie principal de trabajo.

Windows-firstTauri 2 + React + TypeScript Codex DesktopCodex Router Custom agentsSkill local MCP opcionalSin VS Code

01 · Decisión de producto

Decisión principal

No construir una extensión de VS Code ni reemplazar Codex. Construir una aplicación desktop independiente, Codex Orchestra, que actúe como control plane local. Codex seguirá siendo el execution plane y la interfaz donde se conversa con Sol.

Aplicación desktop

Orchestra Control Plane

Configura proveedores, roles, agentes, políticas, diagnóstico, costos, actualizaciones y proyectos sin pedir al usuario tocar TOML, JSON o terminal.

Integración Codex

Skill + agentes + router

La app instala/genera una skill privada de Codex, agentes especializados y la configuración necesaria para que Sol delegue de forma consistente.

Motor externo

Codex Router como dependencia

No reimplementar en v1 el complejo puente Responses ↔ proveedores. Gestionar una versión fijada de duolahypercho/codex-router y envolverla con una UX propia.

Futuro

App Server / MCP

Agregar integración profunda de actividad y herramientas sólo después de tener routing, seguridad y agentes estables. App Server por stdio, no WebSocket, para el MVP.

Por qué esta es la mejor forma: desacopla la UI, la orquestación y los proveedores. Si mañana cambia Grok, Kimi, Codex Router o el modelo root, no hay que reescribir la aplicación completa.

02 · Objetivos y límites

Objetivo A

Un botón para dejar Codex listo con un equipo multi-modelo verificable.

Objetivo B

Elegir roles/modelos visualmente y generar la configuración correcta.

Objetivo C

Detectar errores antes de que una tarea real queme tiempo o API.

Objetivo D

Medir consumo y costo por modelo/rol/proyecto.

Objetivo E

Actualizar y revertir router/configuración de forma segura.

Objetivo F

Que el usuario trabaje normalmente desde Codex Desktop.

No objetivos del MVP

  • No construir un IDE.
  • No clonar la interfaz completa de Codex.
  • No implementar nuestro propio proxy multi-provider desde cero.
  • No almacenar API keys en SQLite, JSON, logs ni estado de frontend.
  • No dejar a Kimi y Grok editar indiscriminadamente el mismo conjunto de archivos en paralelo.
  • No depender de funciones experimentales como WebSocket de App Server para operaciones críticas.

Principio de responsabilidad

Sol decide. Kimi diseña/implementa frontend. Grok implementa ingeniería general. Orchestra configura y observa. Codex Router transporta.

La aplicación no necesita leer el razonamiento privado de los modelos ni meterse dentro de cada token. Debe controlar configuración, identidad del worker, permisos, estado, métricas y resultados observables.

05 · Routing multi-modelo

Política por defecto

ROOT / ORCHESTRATOR
model: GPT-5.6 Sol
responsabilidades:
  - entender la solicitud
  - inspeccionar arquitectura
  - definir contratos compartidos
  - decidir si delegar
  - integrar
  - revisar
  - validar resultado final

FRONTEND
model: Kimi K3
responsabilidades:
  - UI / UX
  - React / Next / RN
  - layout / CSS / responsive
  - accesibilidad
  - fidelidad visual
  - componentes y animaciones

ENGINEER
model: Grok 4.6
responsabilidades:
  - backend
  - APIs
  - base de datos
  - auth
  - lógica de negocio
  - refactors
  - integraciones
  - tests y debugging

Reglas de decisión

  • Trivial: Sol puede resolver directamente.
  • Frontend visual: Kimi.
  • Backend/lógica: Grok.
  • Full-stack: Sol define contrato y delega por ownership.
  • Arquitectura delicada: Sol conserva la tarea.
  • Bug bloqueado: un retry al mismo worker; luego escala a Sol.
  • Review final: siempre root.
Paralelismo: sólo cuando los scopes de escritura no se solapan. Si se solapan, ejecutar secuencial o usar worktrees.

Ownership de archivos

{
  "frontend": {
    "prefer": ["app/**", "src/app/**", "components/**", "src/components/**", "styles/**", "public/**"],
    "denyByDefault": ["db/**", "server/**", "infra/**"]
  },
  "engineer": {
    "prefer": ["server/**", "api/**", "db/**", "services/**", "tests/**", "infra/**"],
    "denyByDefault": ["design/**"]
  },
  "shared": ["package.json", "types/**", "schemas/**", ".env*", "migrations/**"]
}

Los paths son hints/política, no supuestos universales. Orchestra debe permitir que cada proyecto los edite.

06 · Seguridad y límites

Secrets

Delegar almacenamiento de credenciales a Codex Router/almacén seguro del SO. Orchestra sólo conoce configured / missing / invalid.

Config

Escritura atómica, backup previo, bloque administrado con marcadores, nunca sobreescribir config ajena completa.

Procesos

Argument arrays, sin concatenar shell strings. Sanitizar paths. No ejecutar comandos arbitrarios provenientes del UI.

Red

Servicios locales bind a 127.0.0.1. Sin CORS público. No exponer puertos a LAN.

Logs

Redacción de secrets y capability URLs. Opción de no guardar prompts/respuestas.

Updates

Pin de versión/commit, checksum cuando aplique, health check antes de promover update y rollback automático.

Regla dura: Orchestra nunca debe pedir una API key dentro de un chat de Codex. Si hay que introducir una key, la app abre un input local seguro o invoca el helper oficial/seguro del router.

07 · UX del programa

Pantalla 1 · Home

  • Codex Desktop: detectado / versión / autenticado.
  • Codex Router: running / versión fijada / update disponible.
  • Kimi: conectado / modelo / última prueba.
  • xAI: conectado / Grok 4.6 / última prueba.
  • Equipo activo: Sol → Kimi + Grok.
  • Botón Run full health check.

Pantalla 2 · Team Builder

Tres tarjetas editables: Root, Frontend, Engineer. Selector de modelo, effort, descripción, permisos, paths y política de retry.

Pantalla 3 · Projects

Agregar repo local. Orchestra detecta stack y genera un perfil. Preview de cambios antes de escribir: .codex/agents/, skill/config de proyecto y bloque de AGENTS.md.

Pantalla 4 · Diagnostics

Doctor del router, catálogo, subagents disponibles, tool-call test, compaction test, real Codex agent check, proceso y puertos.

Pantalla 5 · Usage

Tokens/costo estimado por día, modelo, provider, proyecto y rol. Presupuesto mensual y alertas visuales. Sin telemetría externa.

Pantalla 6 · Advanced

Backups, rollback, logs redacted, paths, engine pin, export/import de perfil, feature flags y modo experimental App Server.

09 · Integración con Codex Router

Tratar al router como engine externo con adapter. Nunca dispersar comandos del router por todo el código.

trait RouterEngine {
  detect() -> EngineStatus
  install(version) -> Result
  doctor() -> HealthReport
  list_providers() -> Provider[]
  enable_provider(id) -> Result
  provider_credential_status(id) -> CredentialStatus
  list_models() -> Model[]
  curate_model(provider, model, metadata) -> Result
  set_subagent_mode(mode) -> Result
  enable_subagent(model) -> Result
  refresh_catalog() -> Result
  update(target) -> Result
  rollback() -> Result
}

Secuencia de onboarding

  1. Detectar Codex y versión.
  2. Verificar login nativo de OpenAI sin leer credenciales.
  3. Instalar/validar Codex Router en una versión fijada.
  4. Configurar Kimi API y xAI API mediante flujo local seguro.
  5. Confirmar que kimi-api/kimi-k3 existe.
  6. Confirmar/curar grok-api/grok-4.6 si aún no viene en registry.
  7. Ejecutar compatibilidad real con tool use.
  8. Activar sólo Kimi y Grok como candidates de subagent.
  9. Generar agentes de rol.
  10. Reiniciar Codex cuando el catálogo lo requiera.
  11. Ejecutar smoke test Sol → Kimi y Sol → Grok.
No acoplar el producto al slug para siempre. Los slugs de modelos cambian. Guardar un ModelBinding lógico (frontend, engineer) y resolverlo contra el catálogo actual.

Skill privada orchestra-routing

---
name: orchestra-routing
description: Route substantial coding work to Orchestra's configured specialist subagents.
---

# Orchestra routing policy

The current Codex thread is the root technical lead.

Use the frontend agent for substantial visual/frontend work.
Use the engineer agent for substantial backend, data, integration,
testing, refactoring, or general implementation work.

For full-stack work:
1. Inspect the repository and define shared contracts first.
2. Determine write scopes.
3. Delegate in parallel only when write scopes are disjoint.
4. Otherwise delegate sequentially.
5. Wait for delegated results before integration.
6. Root owns shared files, final review, integration and final verification.

Do not delegate trivial changes merely to use an agent.
Retry a failed worker at most once when the failure is transient or clearly repairable.
Escalate unresolved ambiguity or architectural conflict to root.
Never expose provider credentials to a subagent prompt.

12 · Tests y evals

Unit tests

  • Render de agentes y managed blocks.
  • Parser/status del router.
  • Redacción de secretos.
  • Backups y rollback.
  • Resolución model binding → slug.
  • Cost engine.

Integration tests

  • Fake CODEX_HOME: nunca tocar la instalación real durante test.
  • Router adapter con fixture de stdout/stderr.
  • Write atomic + rollback ante fallo.
  • Windows path con espacios y caracteres no ASCII.

Live evals con costo explícito

  • Kimi puede ejecutar una herramienta real y leer el resultado.
  • Grok puede ejecutar una herramienta real y leer el resultado.
  • Sol puede spawn Kimi por tipo de agente.
  • Sol puede spawn Grok por tipo de agente.
  • Full-stack fixture: Sol divide correctamente la tarea.
  • El worker no se sale de scope.
  • Compaction/replay no rompe el handoff.
Cada live eval debe mostrar antes: qué proveedor se cobrará, qué modelo y qué test se ejecutará.

14 · Criterios de aceptación del MVP

  1. Instalación Windows sin necesidad de VS Code.
  2. El usuario puede completar setup sin editar archivos manualmente.
  3. GPT‑5.6 Sol nativo sigue disponible y operativo en Codex.
  4. Kimi K3 y Grok 4.6 están configurados, autenticados y verificados.
  5. Hay un agente frontend pinneado a Kimi y un engineer pinneado a Grok.
  6. Sol puede delegar a ambos y recoger resultados.
  7. Orchestra puede aplicar y revertir sus cambios sin destruir configuración previa.
  8. Ningún secreto aparece en logs, DB, HTML, prompts ni archivos de proyecto.
  9. El dashboard health detecta un router caído, una key inválida y un modelo ausente.
  10. El usuario puede ver consumo/costo estimado por modelo.
  11. Un update fallido del router se puede revertir.
  12. La app permanece pequeña y con consumo razonable de RAM en idle.

16 · Base técnica investigada

La arquitectura se apoya en estas capacidades actuales, verificadas el 12‑08‑2026:

  • Codex local soporta subagentes y custom agents con configuraciones/modelos diferentes; instrucciones de AGENTS.md o skills pueden solicitar delegación.
  • Codex App Server es la interfaz oficial para integrar Codex profundamente en otro producto; el transporte WebSocket está marcado como experimental, por eso no se usa como dependencia crítica del MVP.
  • Plugins pueden incluir skills y conectores/MCP, y están disponibles en Codex dentro de ChatGPT Desktop; una skill standalone es suficiente para el routing inicial.
  • Codex Router traduce/encamina modelos externos y ya gestiona catálogo, providers y custom routed agents; por eso conviene envolverlo en vez de reimplementar el bridge.
